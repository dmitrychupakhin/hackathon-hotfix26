## Предпросмотр документов и прогресс чата

Просмотрщик находится в `src/_pages/chats/ui/`: PDF показывается локальным PDF.js, DOCX — локальным worker и очищенным представлением структуры, TXT/MD — исходным каноническим текстом. Другие поддерживаемые форматы AI возвращает как TXT. Редактирования нет. На широком экране документ расположен справа от переписки, на узком — в правой выдвижной панели. При открытой панели на средних экранах история обсуждений скрывается, чтобы переписка оставалась читаемой, и возвращается после закрытия.

Источник в ответе — простая ссылка `файл.pdf[«цитата»]`, без карточки и кнопки копирования. PDF открыт целиком в непрерывной прокрутке всех страниц; вне видимой области сохраняются места страниц, а canvas подгружается по мере прокрутки, чтобы ограничить память. Нажатие на источник переводит к цитате внутри оригинального документа. Отдельный дублирующий блок извлечённого текста не показывается; полный текст доступен как явный запасной режим при проблеме отображения или точного выделения оригинала.

Цитата открывает файл и точный диапазон текста с проверкой версии и хеша. В оригинальном PDF/DOCX выделяется только однозначное совпадение; точные координаты относятся к извлечённому тексту. Word-пагинация не воспроизводится. Ссылка на место использует fragment URL; JWT и сервисные ключи в неё не попадают. Сессия и ссылка сохраняются при обновлении access token. При необходимости входа используется проверенный локальный `next`.

`run-stream-api.ts` получает реальные `harness.step`, дедуплицирует их по seq и восстанавливает журнал через сгенерированный Django API каждые2секунды, если WebSocket недоступен. UI показывает до восьми основных фаз. После завершения Django сначала дочитывается журнал AI. История сообщений содержит сохранённые цитаты и полный ответ.

При запуске напрямую через Next.js используйте:

```bash
API_ORIGIN=http://127.0.0.1:8000 AI_ORIGIN=http://127.0.0.1:8010 npm run dev
```

`API_ORIGIN` — Django без суффикса `/api`, `AI_ORIGIN` — внутренний origin AI без `/ai` и `/v1`. `/ai/api/v1/runs/{id}/ws` теперь проксируется Next.js, поэтому обход через nginx не обязателен. Если `AI_ORIGIN` не задан, путь `/ai/...` отправляется в nginx по `API_ORIGIN`. Разрешённый Origin страницы должен быть настроен у AI. В Docker defaults: `http://django:8000` и `http://ai:8000`. Rewrites production фиксируются при сборке: для изменения адресов задайте соответствующие Docker build args и пересоберите frontend, одного изменения runtime environment недостаточно.

Клиент API обновляется из текущего backend Swagger: `API_SCHEMA_URL=/path/to/schema.json npm run api:generate`. Новые backend-поля и маршруты описаны в [backend/chats/README.md](../backend/chats/README.md).

## API: генерация для браузера и сервера Next.js

`npm run api:generate` один раз загружает OpenAPI-схему с
https://company-corp.ru/api/schema/ и создаёт два клиента из одного снимка:

- RTK Query hooks и типы для Client Components;
- SDK-методы, типы и фабрики API для Server Components.

Операции распределяются по тегам backend:

| Тег | Модуль | Текущие операции |
| --- | --- | --- |
| Авторизация | `auth` | Вход, refresh и выход (4) |
| Регистрация | `registration` | Регистрация и подтверждение (2) |
| Личный кабинет | `account` | Профиль, фото, смена и восстановление пароля (9) |
| Пользователи | `users` | Пользователь по ID (1) |
| Чаты | `chats` | Чаты, сообщения, файлы и runs (16) |
| Сравнения | `comparisons` | Создание, история, результат, CSV и JSON отчёт (5) |

Сопоставление тегов задаётся в `api.config.ts`. Ручных списков URL,
HTTP-методов, operationId, хуков и типов нет. Отсутствующие/неизвестные теги,
неоднозначное распределение и дубли operationId останавливают генерацию.
Все результаты сначала подготавливаются во временной директории; публикация
начинается только после успешной генерации обоих клиентов для всех групп.

### Где находятся настройки и скрипты

`api.config.ts` — единственная ручная конфигурация: адрес схемы и сопоставление
тегов с модулями. Для добавления группы меняется этот файл.

```text
scripts/
  api/
    generate.ts       # команда генерации
    clean.ts          # команда очистки
    lib/
      schema.ts       # разбор схемы, теги и проверка конфигурации
      generation.ts   # генераторы RTK Query и серверного SDK
      output.ts       # безопасная публикация и очистка файлов
  assets/
    generate-auth-refraction.mjs

tests/
  api/
    unit/             # схема, генерация, публикация, кэш
    server/           # cookies, транспорт и серверные границы
    fixtures/         # вспомогательные модули тестов
  ui/                 # проверки визуальных вычислений
```

`npm run test:api` запускает проверки API, `npm run test:ui` — проверки UI.
Генератор визуального ресурса оставлен в `scripts/assets/`: он нужен для
воспроизведения существующего эффекта стекла и не участвует в API-генерации.

### Теги apiModules: подсказки и полный отчёт

Значения справа в `apiModules` типизированы через OpenApiTag из автоматически
создаваемого `__generated__/schema-tags.ts`. Ключи слева — выбранные разработчиком
имена модулей; значения справа должны точно совпадать с тегами backend.
Типы проверяют допустимость значений и полное покрытие тегов. Отдельная runtime-
проверка также обнаруживает повторное назначение тега разным модулям.

`npm run api:generate` сначала читает свежую схему и обновляет снимок тегов, затем
показывает количество операций/тегов, число сопоставлений и все проблемы сразу:
пропущенные теги с их операциями, устаревшие значения, дубли и неоднозначные
операции. Учитываются только теги, используемые операциями, а не неиспользуемые
объявления в корневом списке tags.

```text
OpenAPI: операций — 12, тегов — 5
apiModules: групп — 4
Сопоставлено тегов: 4/5
Не хватает сопоставлений: 1
  • Документы — операций: 1
    GET /api/documents
```

Это пример появления нового тега, а не текущий контракт. При таком отчёте нужно
добавить соответствие, например `documents: "Документы"`, и повторить генерацию.
Новый тег будет доступен в подсказках редактора после обновления снимка. Ошибка
в типе MissingApiModuleTags означает, что не все теги схемы представлены в apiModules.

**Снимок тегов обновляется даже при ошибке сопоставления**, чтобы TypeScript и IDE
видели новые значения. Остальные API-файлы остаются от последней успешной генерации.
Поэтому до исправления apiModules проверка типов может намеренно завершаться
ошибкой. Если схему не удалось загрузить или разобрать, прежний снимок сохраняется.

При успешной генерации выводится таблица по каждой группе: число операций схемы,
RTK endpoints и SDK-методов. Итог содержит общие количества и число записанных
файлов. Все значения вычисляются автоматически. Проверка типов сопоставления
выполняется отдельно от приложения и не требует уже существующих SDK/hooks:
после api:clean одна команда api:generate создаёт сначала теги, затем оба клиента.

### Что генерируется, а что редактируется вручную

**Всё внутри `src/shared/api/__generated__/` генерируется автоматически.**
Все остальные файлы API, конфигурация и скрипты генератора — ручной код.
Генерация не переписывает ручные файлы.

```text
shared/api/
  __generated__/               # АВТОМАТИЧЕСКИ: весь каталог
    README.md                  # Правила работы с generated-файлами
    schema-tags.ts             # Свежие теги схемы и тип OpenApiTag
    account/
      rtk.ts                   # Endpoints и типы RTK Query
      client.ts                # Готовые экспорты hooks и типов
      server.ts                # getAccountServerApi() и типы SDK
      manifest.json            # Операции/хуки для тестов
      sdk/                     # SDK Hey API и HTTP-клиент
    auth/
    registration/
    users/

  account/                     # ВРУЧНУЮ
    account-api.ts             # Правила кэша
    index.ts                   # Клиентский публичный вход
    index.server.ts            # Серверный публичный вход
  auth/                        # ВРУЧНУЮ: входы и правила login
  registration/                # ВРУЧНУЮ: публичные входы
  users/                       # ВРУЧНУЮ: входы и правила кэша
  base-api.ts                  # ВРУЧНУЮ: общий RTK Query API
  server-request-config.ts     # ВРУЧНУЮ: cookies и API_ORIGIN
  server-transport.ts          # ВРУЧНУЮ: серверный транспорт и ошибки
```

Публичные index.ts и index.server.ts — стабильные ручные переэкспорты. Они
автоматически открывают новые hooks, типы и методы из соответствующего generated
модуля без перечисления операций. Прикладной код использует публичные входы,
а не напрямую __generated__.

### Генерация и очистка

```bash
npm run api:generate   # Создать или полностью обновить __generated__
npm run api:clean      # Удалить только __generated__
```

Очистка не затрагивает ручные настройки, публичные входы, скрипты или конфигурацию.
Повторная очистка при отсутствии каталога тоже успешна. Произвольный путь в команду
передать нельзя; каталог определяется относительно проекта, а не текущей папки.
**После очистки перед проверкой типов, тестами API или сборкой нужно снова выполнить
`npm run api:generate`.** Без generated-кода публичные входы не смогут разрешить импорты.

Генерация не запускает предварительную очистку: сначала обновляется снимок тегов,
затем оба клиента полностью подготавливаются и заменяется весь generated-каталог.
Устаревшие результаты исчезают при замене; ошибка подготовки сохраняет предыдущий
код API. Единственное отдельное обновление — диагностический schema-tags.ts. При ошибке замены
восстанавливается резервная копия. Если восстановление невозможно из-за ошибки
файловой системы, скрипт сообщает путь к сохранённой резервной копии.

Сгенерированные файлы хранятся в Git и не редактируются вручную. Типы двух
генераторов могут иметь разные имена: оба набора происходят из одной схемы,
ручной копии DTO нет. Типы удаляются из JavaScript при сборке; проверки
фактического JSON во время выполнения по умолчанию не добавляются.

### В браузере

```tsx
"use client";

import { useUsersMeRetrieveQuery } from "@/shared/api/account";

export function Profile() {
  const { data, isLoading, error } = useUsersMeRetrieveQuery();
  if (isLoading) return <p>Загрузка…</p>;
  if (error) return <p>Не удалось загрузить профиль</p>;
  return <p>{data?.email}</p>;
}
```

Хуки используются под StoreProvider. Запросы идут на `/api/...` текущего домена,
а Next.js fallback rewrite пересылает их на backend. `credentials: "include"`
передаёт cookies. Route Handlers, если они появятся, имеют приоритет над rewrite.
Store создаётся на экземпляр Provider и сохраняется между переходами.
При Cache Components Provider находится под Suspense: инициализация внутренних
случайных ID RTK выполняется вне статической оболочки.

### На сервере Next.js

```tsx
import { getAccountServerApi } from "@/shared/api/account/index.server";

export async function ServerProfile() {
  const api = await getAccountServerApi();
  const profile = await api.usersMeRetrieve();
  return <p>{profile.email}</p>;
}
```

При использовании компонента с данными текущего запроса поместите его под
Suspense/loading boundary согласно правилам Cache Components.
Аналогичные фабрики доступны для auth, registration и users. Аргументы и
возвращаемые значения SDK выводятся автоматически. Например:

```ts
import { getUsersServerApi } from "@/shared/api/users/index.server";

const api = await getUsersServerApi();
const user = await api.usersRetrieve({ path: { id: 42 } });
```

Фабрика создаёт новый клиент текущего вызова, автоматически читает cookies
через Next.js cookies() и обращается непосредственно к API_ORIGIN, без rewrite.
Cookies не сохраняются в глобальном клиенте и не смешиваются между запросами.
Внутри фабрик используются flat SDK-функции с явным клиентом: классовый SDK
генератора имеет глобальный реестр экземпляров, поэтому здесь не применяется.

Серверные запросы используют `cache: "no-store"`, не следуют redirect и направляют
cookies только фиксированному API_ORIGIN. Остальные входящие заголовки запроса
страницы автоматически не копируются. Аргументы SDK не позволяют переопределять
клиент, origin, fetch, режим кэша или обработку ошибок.

HTTP-ошибка выбрасывает ServerApiError со статусом и телом backend; сетевая ошибка
передаётся вызывающему коду. Автоматических redirect, refresh и уведомлений нет:

```ts
import { getAccountServerApi, ServerApiError } from "@/shared/api/account/index.server";

try {
  const api = await getAccountServerApi();
  const profile = await api.usersMeRetrieve();
} catch (error) {
  if (error instanceof ServerApiError && error.status === 401) {
    // Страница решает, как показать отсутствие авторизации.
  } else {
    throw error;
  }
}
```

Серверные входы и SDK помечены server-only; не импортируйте их из Client Components.
Все методы изменения данных тоже генерируются, но первая интеграция поддерживает
чтение в Server Components. Формы, login и refresh используют браузерный RTK Query.
SDK сам не передаёт Set-Cookie из backend в браузер: для серверного входа/refresh
понадобится отдельная интеграция с Server Actions или Route Handlers.

### Окружение и cookies

Серверная переменная API_ORIGIN задаёт origin backend без пути и `/api`.
Пример — `.env.example`, значение по умолчанию — https://company-corp.ru.
Изменение переменной требует перезапуска dev-сервера или пересборки приложения
для обновления rewrites.

Backend должен выдавать cookies с совместимыми Domain, Path, Secure и SameSite
и принимать фактический Origin/CSRF-контекст фронтенда. Rewrites их не исправляют.
Для авторизованного серверного чтения cookies должны приходить на запрос страницы:
cookie с Path=/api не будет отправлена браузером при открытии /profile.
Работа авторизации с реальными cookies проверяется при подключении формы входа.

### Кэш и независимая загрузка

Все RTK Query группы расширяют один baseApi через injectEndpoints. Store и
Provider импортируют только baseApi. Общего runtime-индекса всех групп нет:
импорт account не подключает auth, registration или users и серверный SDK.
Серверные входы не импортируют Redux и не регистрируют клиентские endpoints.
Next.js может объединять chunks и заранее загружать маршруты; группа исходных
файлов не гарантирует отдельный HTTP-файл.

Ручные правила кэша живут в auth-api.ts, account-api.ts и users-api.ts.
Эти файлы экспортируют настроенный API, без списков хуков. Генератор формирует
экспорты hooks из настроенного API автоматически; при отсутствии ручного модуля
использует соответствующий generated API напрямую.
CurrentUser описывает /users/me, User с ID — /users/{id}. Успешные PUT/PATCH
профиля инвалидируют обе группы, ошибки сохраняют кэш. Активные подписки
обновляются, неиспользуемые записи удаляются. Общая инвалидация User нужна,
поскольку ответ изменения профиля не содержит ID.

Успешный login очищает прежний API-кэш; неуспешный сохраняет его. /me загружается
при появлении потребителя. Неиспользуемые записи хранятся 60 секунд, активные
запросы обновляются при фокусе и восстановлении соединения. Persistence и polling
не включены; поля форм остаются локальным состоянием.

Серверный SDK и браузерный RTK Query не синхронизируют данные автоматически.
Гидратация кэша, серверные изменения и подключение реальных экранов не входят
в эту основу. Пустые login/refresh ответы RTK-генератор описывает как unknown;
это не данные пользователя.

### Добавление операций

1. Backend публикует обновлённую OpenAPI-схему с тегом операции.
2. Выполнить `npm run api:generate`.
3. Использовать готовый hook, тип или серверный метод из нужного публичного входа.
4. Если изменение затрагивает другие данные — дополнить ручные правила кэша.

Для нового тега добавить сопоставление в api.config.ts. Генерация создаёт
его результаты внутри __generated__ автоматически. Один раз добавить ручные
`<модуль>/index.ts` и `<модуль>/index.server.ts` с переэкспортами из generated-группы,
по образцу существующих входов. Ручной `<модуль>-api.ts` добавляется только если
нужны особые правила кэша. Для новых операций существующей группы менять входы не нужно.
Не импортируйте группы из baseApi, store или общего runtime-индекса.

Проверки: `npm run test:api`, `npm run typecheck`, `npm run lint`, `npm run build`.
Тесты проверяют RTK Query с настоящим store, независимость импортов, появление
новой операции без ручных экспортов, серверные cookies и HTTP/сетевые ошибки.
Ожидаемые endpoints и hooks берутся из generated manifests, без фиксированных
списков. Серверные тесты подменяют только Next request context/server-only marker
и fetch в отдельном процессе; production-код этих подмен не содержит.
Дополнительно проверяются очистка, восстановление после очистки, удаление
устаревших артефактов и сохранность прежнего результата при ошибке публикации.


### Сравнение по кейсу ОНСОФТ (`/comparisons`)

Загрузите `questions.csv` и `answers_public.json` организатора в соответствующие
поля. Их структуру читает код сервера; отвечающая модель не получает эталоны.
Для шести закупок загрузите один ZIP с файлами **TXT/MD** в папках
`packages/P01/...` … `packages/P06/...`. Другие форматы внутри ZIP отклоняются.
PDF, DOCX и другие оригинальные документы загружайте отдельными файлами только
одной закупки. До 10 МиБ на загружаемый файл, до 32 МиБ суммарно загрузки;
размер распакованных данных также ограничен сервером (128 МиБ на ZIP,
32 МиБ на закупку).
Базовая версия делает один запрос с документами и всеми вопросами закупки;
харнесс использует ту же модель и ту же группировку, добавляя проверки и исправления.
Профильные инструкции дополняют основной промпт харнесса так же, как в чате.

Во время запуска экран показывает реальный шаг из `progress.run_states[mode].step`:
`title`, `message` и номер порции `details.batch/details.batches`, когда он есть.
Тексты документов и сырые параметры инструментов не выводятся в прогрессе.
Если `metrics_final=false`, количество генераций обозначено как начатые запросы;
это промежуточные данные, а не окончательный расход.

После завершения экран показывает индекс доверия по формуле задания,
разбивку по категориям, ответы и цитаты двух режимов, причины оценки и
сработавшие проверки. Расходы берутся из сохранённых метрик: запросы, время,
входные/выходные токены и стоимость, если тариф известен. `model_calls` —
логические генерации; `transport_attempts` — фактические HTTP-попытки, включая
повторы после 429. Второе число показывается только если оно сохранено в метриках;
для старых запусков его не вычисляем из количества генераций. Отсутствующий тариф
не заменяется предполагаемой ценой. Технический отказ одного режима
показывается отдельно с `Н/Д`; индекс второго режима сохраняется, прирост
между несопоставимыми результатами не рассчитывается.

Кнопки скачивания используют generated RTK Query операции
`comparisonsAnswersRetrieve` (`mode=baseline|harness`) и
`comparisonsReportRetrieve`. Запросы идут с cookies через общий refresh-механизм;
ключи и JWT не помещаются в URL. CSV содержит исходные ID вопросов и колонки
`id;status;answer;quote;file`. JSON сохраняет подробности для воспроизводимости.
Blob URL существуют только на время подписки компонента и освобождаются при
смене загрузки или уходе со страницы.

Проверка вручную: загрузить официальный набор, выбрать одну модель,
дождаться обоих режимов, раскрыть вопрос с изменившейся оценкой и сравнить
цитаты/причину ошибки. Скачать оба CSV и проверить каждый оригинальным
`check.py`. Если большой контекст привёл к техническому отказу baseline,
ожидается `Н/Д` с причиной отказа, а не нулевой индекс и не скрытый результат
харнесса. При одинаковых верных ответах улучшение равно нулю.
