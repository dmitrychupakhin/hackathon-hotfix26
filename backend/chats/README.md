# Чат, источники и события AI

Backend хранит пользователей, чаты, сообщения и метаданные вложений. AI читает каталог `ai.files` в общей PostgreSQL и исходники через read-only volume, извлекает канонический текст и выполняет запрос. Команда `python manage.py run_chat_worker` отправляет задания и сохраняет итоговые ответы. Django ID запуска и AI ID различаются: браузер использует Django URL и возвращённый сервером путь WebSocket.

Раздел «Инструкции для ИИ» сохраняет текст в `User.system_prompt`. У новых пользователей есть базовые инструкции по закупочной документации; миграция `users.0004_default_ai_instructions` заполняет только существующие пустые профили, не перезаписывая личные тексты. Поле видно в редакторе и доступно для изменения. Явное сохранение пустого поля по-прежнему убирает пользовательские инструкции. Снимок инструкций применяется к следующему сообщению, предыдущие ответы не пересчитываются.

## Обновление и запуск

1. `python manage.py migrate --noinput` применяет схему AI, `0005_message_evidence` и каталог моделей `0006_model_catalog`.
2. Настроить `AI_BASE_URL`, одинаковый `AI_SERVICE_KEY` у Django/AI и общий source volume. Ключ провайдера `APIMIRA_API_KEY` получает только AI.
3. Запустить Django, AI с одним worker и `python manage.py run_chat_worker`.
4. При настроенном провайдере выполнить `python manage.py sync_ai_models`: команда сверяет доступность шести моделей по каталогу AI, не делает платных генераций и не отключает модели при недоступном каталоге.

`GET /api/chats/models` возвращает `id` для API и читаемое `name` для интерфейса. Одна модель выбирается для сообщения/чата; одновременных ответов нескольких моделей нет. По умолчанию используется активная `APIMIRA_MODEL`, иначе GPT-6 Luna при стандартной конфигурации. Пользовательские названия и отключения существующих моделей миграция не перезаписывает. Модели в начальном каталоге: GPT-6 Luna, GPT-6 Astra, GPT-5.4 Mini, Claude Sonnet 4.6, Gemini 3 Flash Preview, DeepSeek V4 Flash. Наличие в каталоге не гарантирует качество или идентичные возможности инструментов разных моделей.

## Контракты для frontend

- История сообщений возвращает `content`, read-only `answer_payload` и `citations`; старые сообщения не получают доказательства задним числом.
- `GET /api/chats/{chat_id}/files/{file_id}/preview` возвращает канонический текст, формат, хеш, версию и страницы. `GET .../content` отдаёт исходный PDF/DOCX, остальные поддерживаемые форматы — UTF-8 TXT. Оба URL авторизованы; токен в ссылке не нужен.
- Цитата привязана к ID файла, версии, SHA-256 текста и диапазону Unicode code points `[start,end)`. Устаревший источник возвращает 409. Подробности: [document-preview.md](../../ai/docs/document-preview.md).
- `POST /api/chats/{chat_id}/runs/{id}/ws-ticket` возвращает путь `/ai/api/v1/runs/{AI_ID}/ws`. До создания AI run —409. Наблюдать нужно по возвращённому пути, а не собирать его из Django ID.
- `GET .../runs/{id}/events?after=0&limit=100` — резервный журнал реальных событий; максимум500. Он используется и после терминального статуса, чтобы дочитать последние шаги. `Chat.latest_run` позволяет восстановить запуск после обновления страницы.

Основные UI-шаги приходят как `type=harness.step`; интерфейс объединяет повторные операции по фазам. Независимое чтение источников и решение критика отображаются отдельно: успешное чтение не означает успешную проверку ответа. События не содержат поток скрытых рассуждений модели. Полный контракт: [websocket-events.md](../../ai/docs/websocket-events.md). Подготовка файлов до создания AI run пока не имеет отдельного run-потока.

Swagger: `/api/docs/swagger/`, схема `/api/schema/`. Для локального обновления frontend-клиентов можно скачать JSON схемы и передать `API_SCHEMA_URL=/path/to/schema.json npm run api:generate`.

## Несколько вопросов в одном сообщении

`POST /api/chats/{chat_id}/messages` принимает одно `content` и создаёт одно пользовательское сообщение. При наличии документов AI `/api/v1/chat-runs` передаёт **полное сообщение модели**, которая выделяет независимые части ответа по смыслу — включая CSV/TSV, обычный текст и вопросы в одной строке. Регулярки, ключевые слова и строки не определяют число вопросов. Модель копирует исходные последовательные фрагменты; код проверяет, что ни один значимый символ не потерян, не добавлен и не переставлен. Полное исходное сообщение остаётся общим контекстом для генерации и критика, включая условия и общие инструкции. Нельзя пропустить неудобный вопрос. Не более 50 частей; некорректный план повторяется один раз, затем run завершается `failed / invalid_chat_plan`, без выдачи непроверенных фактов. Это асинхронная ошибка запуска, не синхронный 422 при отправке сообщения.

Одна часть сохраняет ID сообщения; несколько получают `{message_id}.q01`, `.q02`, … . ID из вставленной CSV (например P01-03) — только пользовательские метки, не ID для `submit_answers`. После планирования `request.questions` в AI run обновляется и определяет порядок частей. Исходное сообщение сохранено в snapshot `chat_message` и в Django. Планирование использует ту же выбранную модель и общий бюджет вызовов/времени: обычно один дополнительный запрос, максимум два при неверном плане. Чат без документов остаётся прямым ответом без планирования. Сравнение по готовому `questions.csv` не использует этот шаг и сохраняет исходные ID организатора.

Проверки и исправление выполняются независимо. Успешные ответы остаются принятыми, даже если другой пункт не прошёл проверки. Лимиты **на весь запуск**, не на каждый вопрос: 48 запросов модели, 8 раундов на пакет, 1 попытка исправления ответа. Чат с документами использует дедлайн из `AI_RUN_TIMEOUT_SECONDS` (по умолчанию 1200 секунд, не более 3600); без документов сохраняется предел 600 секунд, ограниченный серверным потолком. Ожидание семафора входит в дедлайн, подготовка файлов до создания run и доставка через worker — нет. Вызовы критика и повторы сканера расходуют общий бюджет LLM; сами локальные инструменты не являются запросами к модели. Выполнение может закончиться раньше лимита времени. Количество вопросов не гарантирует количество LLM-запросов.

Если провайдер независимой проверки недоступен, AI повторяет только упавший запрос один раз. После второго транспортного отказа в чате сохраняются текст и цитаты уже прошедшего проверки кодом фактического ответа. В `answer_payload` остаются `reason=independent_review_incomplete` и неуспешный `checks[].code=review_unavailable`; отсутствие предупреждения в тексте не означает успешный вердикт ИИ. Для «нет в документах» и сравнительных прогонов это послабление не действует.

Worker сохраняет одно сообщение ассистента: `content` содержит полный читаемый ответ, `answer_payload.parts` — упорядоченные независимые результаты с `id`, `question`, `status`, `answer`, `display_answer`, `checks`, `evidence`, `citation_ids`. `partial=true` означает, что хотя бы один пункт остался неопределённым. Верхний `status` — сводный; для оценки конкретного вопроса используйте **статус его parts**, а для официального CSV — исходные AI `result.answers`. Верхний `citations` содержит объединённые ссылки, а `parts[].citation_ids` привязывает их к пунктам. UI размещает обычные ссылки на источники непосредственно под соответствующим ответом. Формат одиночных ответов совместим с прежним.

`answer.completed` приходит отдельно для каждого пункта. Помимо `data.answer` содержит `data.question`, `question_index` (с нуля), `question_count`. Клиент накапливает результаты по ID и показывает их в исходном порядке; ошибка одного пункта не заменяет уже полученные ответы. При fallback показывается причина отказа, например несовпавшая цитата, а не одиночное «не знаю». Старые сообщения/результаты автоматически не пересчитываются.

Большой ответ со списком вопросов хранится в истории целиком. При следующем запросе каждое предыдущее сообщение ограничивается 12000 символами для входного контракта AI, затем применяются его обычные правила компактного контекста. Список файлов хранится отдельно и при сокращении старых сообщений не теряется; старые ответы не становятся источниками фактов.


## Сравнение «было/стало» по заданию

`POST /api/comparisons` принимает multipart: `questions` — исходный **questions.csv**, `answers` — исходный **answers_public.json**, `documents` — один ZIP с каталогами `packages/P01…P06/` либо плоские файлы **одной** закупки; `model_id` необязателен (тогда активная модель по умолчанию). Разделение нескольких закупок по содержимому или имени файла не угадывается. Лимиты: 10 МиБ на файл, 32 МиБ суммарно документов, 64 вложения. ZIP распаковывает и валидирует AI; небезопасный или неоднозначный архив отклоняется. Неподдерживаемые форматы вопросов/эталонов дают 400 до запуска. Некорректное содержимое CSV/JSON либо пакетов завершает подготовку со статусом failed, без платных генераций.

Worker передаёт ID исходных файлов в AI `/comparison-inputs/parse`. Парсер читает CSV/JSON **кодом**, сохраняет ID вопросов, формулировки, категории и эталоны. Эталоны не попадают в промпт отвечающей модели. Полученная карта `progress.package_ids` сопоставляет исходный `P01` с AI UUID; исходный код используется при оценке и экспорте.

Протокол — `question_grouping=per_package` у **обоих** режимов, одна модель и один провайдер, одинаковые вопросы, снимки источников и эталоны. Baseline делает один исходный запрос на закупку, без инструментов, проверок, критика и повторного исправления; цитаты заполняет сама модель. При шести закупках это шесть исходных запросов. Harness использует ту же группировку с проверками и исправлениями. Инструкции профиля добавляются через `additional_instructions` к встроенным правилам harness, как в чате, и не заменяют их. Baseline пользовательские улучшения не получает. Все дополнительные вызовы harness учитываются в метриках.

`GET /api/comparisons/{id}` возвращает `progress.run_states` по режимам, а после выполнения — `result.before` и `result.after`: `available`, `status`, безопасную `error`, количество вопросов, `correct`, `errors`, `careful`, `trust_index`, разбивку `by_type`, строки `rows`, метрики `run_metrics` и `prompt_hashes`. Индекс = `(correct-errors)/questions*100`, как в check.py. `result.protocol` фиксирует модель, группировку, закупки и SHA-256 инструкций без их текста. Технический отказ baseline (например, окно контекста) **не уничтожает** успешный результат harness: у отказавшего режима оценки равны `null`, `available=false`, `delta=null`. Общий status completed означает, что обработка сравнения закончилась; доступность оценок проверяйте отдельно. Разница считается только после парной проверки одинаковых входов. Равные результаты показываются как нулевое улучшение.

Для сравнения `AI_COMPARISON_TIMEOUT_SECONDS=1200` задаёт запрашиваемый бюджет каждого AI режима **20 минут**. Worker сохраняет его в `progress.run_timeout_seconds` до первого запуска и использует одинаковое значение в `options.timeout_seconds` обоих режимов, даже если конфигурация между ними изменилась. Ожидание двух запусков — совместно бюджет + 60 секунд (**1260 секунд** по умолчанию), polling каждые 2 секунды. `result.protocol` фиксирует оба лимита. Подготовка/импорт файлов и вычисление оценки не входят в это ожидание. Серверный `AI_RUN_TIMEOUT_SECONDS` остаётся верхним пределом AI: меньшее значение ограничивает запуск раньше; для полного бюджета сравнения задайте его не меньше 1200. Чаты с документами используют серверный дедлайн; лимиты 48 вызовов и 1 исправления ответа не повышаются. Бюджет сравнения можно уменьшить отдельно через `AI_COMPARISON_TIMEOUT_SECONDS`; увеличение времени не гарантирует завершения контрольных 100 вопросов. При превышении ожидания worker запрашивает отмену незавершённого режима. Оба режима запускаются до ожидания, технический отказ одного не останавливает другой.

- `GET /api/comparisons/{id}/answers.csv?mode=baseline|harness` — готовый CSV выбранного режима для `python check.py answers.csv`: UTF-8, разделитель `;`, ровно `id;status;answer;quote;file`. Переносы строк нормализуются только при экспорте, исходные цитаты сохраняются в JSON. Для технически незавершённого режима — 409, выдуманные строки «не знаю» не создаются.
- `GET /api/comparisons/{id}/report.json` — скачиваемый отчёт: исходные вопросы и эталоны, оба результата, ответы, доказательства и проверки, метрики, хеши промптов, протокол. Для воспроизведения включены зафиксированные инструкции профиля и snapshot промптов завершённых оценок. Ключи провайдера и сервиса не экспортируются. Отчёт доступен только владельцу; до формирования — 409.

Все чтения и выгрузки доступны только владельцу (чужой ID — 404, без входа — 401), ответы не кешируются. Старые сравнения не пересчитываются автоматически: для нового воспроизводимого протокола загрузите набор заново. Старый отчёт без сохранённых исходных ответов не поддерживает CSV-экспорт (409). Эталоны учебного набора служат только измерению; честный ответ на новые вопросы не должен зависеть от их наличия.


Прогресс сравнения: `progress.event_cursors.baseline/harness` сохраняет последний обработанный `seq` AI-журнала. Worker читает owner-scoped `/runs/{id}/events?after=...&limit=100` и отдаёт `progress.run_states.{mode}.step`: только публичные `title`, `message`, `status`, `kind`, `details` из `harness.step`. Исходные prompts, payloads инструментов и тексты документов в этот прогресс не копируются. Вспомогательное «сохранение результата» не затирает последний содержательный этап. `model_calls_started` показывает наблюдаемое число начатых LLM-вызовов; пока `metrics_final=false`, `metrics.model_calls` — максимум записанной метрики и этого счётчика, `model_calls_source=started_events`. Токены и стоимость по началу вызова не оцениваются. После терминального AI статуса возвращаются его точные финальные метрики (`metrics_final=true`, `model_calls_source=final_metrics`); локальный таймаут ожидания не делает неполные метрики финальными.
