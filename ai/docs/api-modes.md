# Режимы ответа AI для backend

Поле `mode` принимается в `POST /api/v1/runs`, `POST /api/v1/datasets/{dataset_id}/runs` и `POST /api/v1/sessions/{session_id}/messages`. В чате доступны только `plain` и `harness`. Значение по умолчанию — `harness`.

| Режим | Поведение | Системный промпт профиля |
| --- | --- | --- |
| `plain` | Один запрос к модели: все документы и вопросы, без инструментов, проверок фактов, критика и исправлений. Проверяется только структура ответа для единого API и CSV | Принимается; иначе встроенные общие инструкции |
| `harness` | Инструменты, проверка доказательств кодом, обработка больших документов, опциональный смысловой критик и ограниченное исправление | Принимается; иначе встроенные инструкции harness |
| `baseline` | Один пользовательский запрос с документами, вопросами и минимальными требованиями к формату ответа; без системного сообщения и проверок фактов | Запрещён, HTTP 422 |
| `raw` | Один пользовательский запрос с исходными документами и вопросами, без инструкций по формату; исходный ответ сохраняется, статусы и доказательства не додумываются | Запрещён, HTTP 422 |

Backend может показывать переключатель «Обычный ответ» (`plain`) / «С проверками» (`harness`). Для замера по заданию также сохранён `baseline`: у него нет системного сообщения. Сравнение должно использовать одну модель и одинаковые документы/вопросы. Изменение системного промпта между запусками также влияет на результат и должно быть явно отражено в отчёте.

Пример сообщения чата:

```json
{
  "text": "Какой размер обеспечения заявки?",
  "mode": "plain",
  "system_prompt": "Ты помощник по закупкам. Используй приложенные документы и отвечай по-русски."
}
```

`system_prompt` передаётся первым сообщением `role=system` **без скрытой правки текста**. В `plain` второе и единственное пользовательское сообщение содержит документы, вопросы, компактное состояние чата и минимальный JSON-контракт результата. Профильный промпт, который требует вызвать `submit_answers`, `calculate` или другой инструмент, не подходит для `plain`, потому что инструментов там нет. Для сравнения с одним профильным промптом используйте общие ролевые правила. Инструкции, специфичные для tools, должны соответствовать выбранному режиму.

`null` или отсутствие поля означает встроенный промпт выбранного режима. Фактически использованный текст и хеш фиксируются в снимке запуска; `system_prompt_source` сообщает `builtin`, `profile` или `not_used`. Полная история чата хранится в БД; модель получает компактное состояние по [chat-context.md](chat-context.md).

Оба основных режима возвращают HTTP 202 и общий объект запуска. Финальный `GET /api/v1/runs/{id}` содержит `status`, `result.answers`, `result.raw_outputs`, `metrics` и `error`. Для `plain` поле `checks` пусто. Если дословная цитата однозначно найдена в указанном файле, `evidence` содержит координаты для навигации с `anchor_method=exact_text_match`; при отсутствии или неоднозначности совпадения список пуст. Это сопоставление положения текста, а не проверка правильности ответа: **успешный запуск и кликабельная цитата не означают, что ответ верный**. Придуманная цитата или неверное число в корректном формате намеренно не отбрасываются — это позволяет измерить пользу проверок harness. Если JSON-формат неверен, запуск завершается `failed` с `plain_format_invalid`; исходный вывод остаётся в `raw_outputs`, повторного обращения к модели нет.

Экспорт обоих режимов: `GET /api/v1/runs/{id}/answers.csv`, разделитель `;`, поля `id;status;answer;quote;file`. Для `raw` статус может быть пустым; такой результат не эквивалентен готовому корректно оформленному CSV.

WebSocket и журнал событий общие для всех режимов: `run.queued`, `run.started`, `llm.started`, `llm.finished`/`llm.failed`, `answer.completed`, `run.completed`/`run.failed`/`run.cancelled`/`run.interrupted`. Событие `harness.step` является общей транспортной формой шага даже при `mode=plain`; `data.kind=plain` означает «Обычный ответ модели без дополнительных проверок». В обычном режиме не должно быть `tool.*`, `validation.*`, `review.*` и `repair.*`. Система может отказать до обращения к модели, если документы не помещаются: `plain` не обрезает их и не включает обход порций автоматически.

Подробности подключения и восстановления WebSocket описаны в основном README. Backend должен определять режим по `run.mode`, а наличие проверок — по результату, не по одному имени события `harness.step`.

Адаптер Django-чата `/api/v1/chat-runs` выделяет до 50 вопросов из явного списка и запускает существующую независимую проверку по каждому ID. Это не LLM-переформулировка: продолжения и условия сохраняются, неоднозначный текст остаётся одним вопросом. Один пункт — исходный `message_id`; несколько — `{message_id}.q01` и далее. Порядок/тексты находятся в `run.request.questions`, ответы — в `run.result.answers`. Неуспешный пункт не отменяет остальные. Все пункты делят обычные лимиты RunOptions (48 вызовов, 8 раундов, 1 исправление; для документов дедлайн из AI_RUN_TIMEOUT_SECONDS, по умолчанию 1200 секунд и не более 3600 секунд на AI run, включая ожидание семафора; подготовка файлов до run учитывается отдельно), а не получают отдельный бюджет. В Django-адаптере документы включают harness автоматически; без документов используется plain. Переключение mode из этой страницы относится к универсальному API runs/sessions/datasets, не к параметрам Django `/chat-runs`.
