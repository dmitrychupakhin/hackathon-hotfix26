# Разбиение источников и независимая проверка

## Размер и происхождение фрагмента

`AI_CHUNK_TARGET_TOKENS=2000`, `AI_CHUNK_OVERLAP_TOKENS=200` — начальные
настройки. Применяется оценка `ceil(число Unicode-символов / 2)`, а не точный
токенизатор модели. Это настройки исходного фрагмента; несколько фрагментов
объединяются в запрос с учётом инструкций, инструментов и резерва ответа.
Окончательный бюджет запроса дополнительно проверяется harness.
При меньшем фактическом окне исходный чанк также уменьшается: не более
четверти окна после резерва ответа (с нижним ориентиром 256 оценочных токенов).
Перекрытие ограничивается четвертью фактического чанка. Поля
`context.prepared.chunk_target_tokens/chunk_overlap_tokens` показывают реальные
значения, а `configured_chunk_*` — исходные настройки. Даже минимальный чанк
может не поместиться вместе с длинными инструкциями; в таком случае действует
контролируемый отказ, а не обещание успешной работы при любом окне.

Граница выбирается на конце предложения, абзаца или строки в пределах бюджета.
Перекрытие старается начинаться с такой же границы. Для очень длинного
предложения/строки действует жёсткий разрез по символам. Обычные строки таблиц
сохраняются целиком, если помещаются в бюджет. Заголовок длинной таблицы может
остаться в предыдущем фрагменте: извлечение структуры таблиц нельзя считать
гарантированным этим текстовым алгоритмом.

Текст не переписывается. `span_id` получается из ID документа, хеша извлечённого
текста и `[start,end)` — координат в неизменённом оригинальном тексте.
`Span.locations` содержит пересекающиеся координаты страниц/слайдов/листов,
если их предоставил парсер. TXT без разметки страниц не получает выдуманных
номеров страниц. Смена исходного текста меняет ID доказательств.

Дубли от перекрытия не считаются независимыми подтверждениями. В журнале фактов
доказательства приводятся к `(document_id, source_hash, start, end)`. Два
отдельных места с одинаковой фразой сохраняются как отдельные источники.

## Большой пакет: поиск, синтез, повторная проверка

В `mode=harness`, `options.context=auto`:

1. Если источники и служебная часть помещаются, генератор получает оригиналы.
2. Если не помещаются, `evidence_scan` обходит **все** исходные фрагменты.
   Модель возвращает выборки и предварительные факты для каждого вопроса.
3. Генератор получает выбранные оригинальные выдержки, все найденные
   конкурирующие факты и статистику покрытия. Ответ пока кандидат.
4. Код проверяет доказательства, числа и расчёты.
5. Если полный контекст критика велик, `verification_scan` независимо обходит
   все оригиналы, получая кандидата, но не выводы первого сканера. Ищет как
   подтверждения, так и опровержения.
6. Критик получает оригинальные выдержки обеих выборок, кандидат, журнал фактов
   и покрытие. Должен проверить поздние изменения, исключения и конфликты.
7. При отклонении запускается ограниченное исправление. При недостаточном
   контексте/покрытии/бюджете система отвечает «не знаю».

`options.context=retrieval` означает чтение инструментами; обязательный полный
первичный проход в этом режиме не обещается. `full` требует полного контекста и
не переключается на сканирование. Режимы `plain`, `baseline`, `raw` не используют
этот цикл. Критик выключается `semantic_review=false`; такой результат нельзя
представлять как прошедший независимую проверку моделью.

## Предварительные факты

Ответ сканера имеет структуру:

```json
{
  "selections": [{
    "id": "P01-01",
    "span_ids": ["source-span-id"],
    "facts": [{
      "field": "обеспечение заявки",
      "value": "18000",
      "unit": "рубли",
      "condition": "",
      "relation": "support",
      "evidence": [{
        "span_id": "source-span-id",
        "quote": "Обеспечение заявки: 18000 рублей."
      }]
    }]
  }]
}
```

`relation`: `support` (потенциальное подтверждение), `refute` (опровержение),
`amendment` (изменение), `exception` (исключение). Это классификация модели,
которая сама требует проверки. Не устанавливает автоматический приоритет.

Каждый вопрос обязан присутствовать в каждой порции; пустые `span_ids/facts`
означают только отсутствие находок **в этой порции**. Для совместимости парсер
принимает старую форму без `facts`; оригинальные выбранные фрагменты всё равно
передаются дальше. Производственный промпт требует структурированные факты.

Код проверяет принадлежность ID текущей порции и дословное вхождение цитаты
(`len(quote.strip()) >= 8`). Поддельная цитата,
неверная схема или незавершённый проход не подтверждают отсутствие сведений.
Проверка дословности не доказывает смысловую верность `field/value/unit`.

Журнал `fact_ledger` сохраняет конкурирующие значения, условия и отношения:
ранняя находка не перезаписывает позднюю. Генератор и критик получают поле
`provisional=true`, координаты доказательств и `observed_in` с именами проходов.
Содержимое scan-ответов сохраняется в `raw_outputs`; события
`context.batch_scanned` содержат число фактов и покрытие. Текст источника,
прежние ответы и журнал фактов всегда рассматриваются как недоверенные данные,
а не инструкции. Даже полный проход не гарантирует, что модель заметила всё.

## Бюджеты и ошибки окна

Все сканирования, генерация, критик и исправления входят в один `max_calls` и
общий лимит времени запуска. При ошибке провайдера `context_length_exceeded`
локальный бюджет уменьшается минимум вдвое и план строится заново из оригиналов.
Уже принятые ответы сохраняются. Действуют предел числа уменьшений и минимальное
полезное окно. Остальные ошибки провайдера не запускают такой повтор.

Если выбранные доказательства вместе с журналом даже для итогового запроса не
помещаются, источники не обрезаются молча: неподтверждённый результат становится
«не знаю». Размер окна модели — верхняя граница, а не обещание вместить любой
диалог или документ.

## Проверки реализации

`tests/test_chunking.py` проверяет бюджет, перекрытие, границы строк, сохранение
хвоста, стабильность ID и изменение версии. `tests/test_fact_ledger.py`
проверяет дедупликацию по оригинальным координатам, сохранение противоречий,
отклонение выдуманных цитат, позднее изменение и передачу обоих значений критику.
Эти тесты используют FakeModel и проверяют код/контракт. Они не доказывают
качество реальной модели.

## Аудит результата

`Harness.audit_state()` возвращает отсоединённый JSON-совместимый словарь по ID
закупки. Для каждой закупки сохраняются revision и `attempts`: планирование после
уменьшения окна создаёт новую попытку, не стирая предыдущую. Попытка содержит
`fact_ledger`, `coverage` по проходам, `original_blocks`, `blocks_read`,
`read_complete`, фактический бюджет контекста и `accepted_question_ids`.
Runner публикует эту структуру в `result.evidence_audit`. Наличие фактов само по
себе не означает, что итог прошёл проверки: для этого смотрите статус и checks
конкретного ответа. Режимы без harness могут вернуть пустой аудит.
